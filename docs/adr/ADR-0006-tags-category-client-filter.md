# ADR-0006：tags 与 category 仅用于列表页前端筛选

- 状态：已采纳（2026-11-08）
- 相关：ADR-0001（无 SSR，筛选只能在前端）、ADR-0002（字段定义）

## 背景

需求方在扩展 frontmatter 时选了 `tags` 与 `category`，但在页面清单里**没有**选分类页与标签页。这构成一个需要澄清的矛盾：字段写进去了，却没有承接它的路由。

一个无人消费的字段是纯粹的负债——它增加写作时的心智负担，增加 schema 校验面，却不产生任何读者可见的价值。

## 决策

`tags` 与 `category` **不生成任何聚合路由**。它们唯一的消费者是 `/blog` 列表页顶部的前端筛选。

具体形态：

- 列表页顶部渲染一排筛选芯片（chip），数据来自构建期对全部文章 `tags` 与 `category` 的去重汇总。
- 点击芯片即在当前页过滤卡片，不跳转、不刷新。
- 筛选状态写入 URL 查询参数（如 `?tag=cloudflare&category=工程`），使筛选结果可分享、可后退、刷新后保持。
- 过滤逻辑由一段轻量客户端 JS 完成：所有文章的元数据在构建期已内联进 DOM（`data-*` 属性），JS 只做显示/隐藏，不发任何请求。
- 芯片同时显示各标签的文章数，让读者一眼看到内容分布。

不做的三件事：

1. 不建 `/tags/[tag]` 与 `/categories/[category]` 路由。
2. 不做文章底部的"相关文章推荐"（需求方未选）。
3. 不做全站搜索。

## 理由

- 前端筛选在纯静态架构下是唯一不引入服务端的选择，且体验比跳转聚合页更流畅——即时反馈、无页面重载。
- URL 参数持久化补上了前端筛选最大的短板：结果无法分享。加上它之后，筛选链接与静态聚合页在"可分享性"上等价。
- 不建聚合页避免了两套等价 UI（芯片筛选 + 聚合页）的重复维护。对一个文章数量在数十到数百量级的博客，筛选已经覆盖了聚合页的全部用途。

## 代价

- **筛选只能作用于已加载到当前页的文章**。若未来文章数增长到需要分页，前端筛选会只筛当前页，语义变得混乱。届时必须重新评估：要么取消分页（全量内联），要么改为构建期生成聚合页，本 ADR 需被推翻。
- 标签页对 SEO 有独立的收录价值（每个标签是一个可被搜索引擎索引的落地页），前端筛选完全没有这个价值。
- 元数据内联进 DOM 会让列表页 HTML 随文章数线性增长。
- 无脚本环境下筛选芯片完全失效，文章列表退化为不可过滤的全量列表（可接受，内容本身仍可读）。

## 备选方案

| 方案 | 否决理由 |
| --- | --- |
| 建 `/tags` 与 `/categories` 聚合页 | 与前端筛选功能重叠，两套 UI 同时维护；需求方在页面清单里明确未选。 |
| 仅作展示徽标 | 字段几乎无价值，等于白写 frontmatter。 |
| 相关文章推荐 | 需求方未选；且同 tag 推荐在文章少的时候会推出噪音。 |
| 全站搜索 | 需构建期生成索引 + 前端搜索库，体量远超"筛选"需求。 |
