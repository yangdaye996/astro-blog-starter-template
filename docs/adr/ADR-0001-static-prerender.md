# ADR-0001：保持纯静态预渲染，不引入 SSR

- 状态：已采纳（2026-11-08）
- 相关：ADR-0004（构建时预渲染富媒体）、ADR-0007（删除 RSS 与 sitemap）

## 背景

本项目运行在 Cloudflare Workers 上，Workers 存在 CPU 时间、内存与存储配额限制。模板来自 Cloudflare 官方的 `astro-blog-starter-template`，`astro.config.mjs` 中未设置 `output`，因此 Astro 默认走 `static` 模式：所有页面在 `astro build` 时预渲染为 HTML，产物落在 `dist/`，`wrangler.json` 通过 `assets.directory` 把它交给 Workers 静态资源托管，`ASSETS` binding 只负责发文件。

需求方最初提出的顾虑是"有内存和存储及 cpu 限制"。经核实，这个顾虑在当前架构下**并不成立**：静态托管路径不执行用户代码，不消耗 Worker 的 CPU 与内存配额。配额只有在引入 SSR（`output: 'server'` 或按路由 `export const prerender = false`）后才会成为真实约束。

## 决策

维持纯静态预渲染。全站不引入任何 SSR 路由，不使用 KV / D1 / R2 等边缘数据绑定。

由此推出的硬约束：

1. 所有交互能力（筛选、TOC 高亮、代码复制）必须由客户端 JS 或纯 CSS 实现，不得依赖服务端。
2. 所有需要重计算的内容（阅读时长、字数、上一篇/下一篇、Mermaid SVG、KaTeX HTML、字体子集）必须在构建期算完并写进 HTML。
3. 任何"写入型"功能（评论、点赞、访问计数）不在本站范围内。若未来需要，必须先另开 ADR 推翻本决策。

## 理由

- 博客是典型的读多写零场景，预渲染能拿到最好的 TTFB 与 Lighthouse 成绩。
- 静态托管不消耗 Worker 计算配额，把需求方担心的限制直接变成非问题。
- 部署链路最短：`astro build && wrangler deploy`，无冷启动、无数据库迁移、无密钥管理。

## 代价

- 内容更新必须走完整的构建 + 部署流程，没有"改一条数据就生效"的能力。
- 无法做个性化渲染（按地区、按登录态、按 A/B 分流）。
- 站内搜索只能是构建期生成索引 + 前端过滤，规模变大后会退化。

## 备选方案

| 方案 | 否决理由 |
| --- | --- |
| 全站 SSR | 每次访问都消耗 Worker CPU 与内存，对博客是纯粹的过度设计，且把配额风险从"不存在"变成"常态化"。 |
| 静态为主 + 少量 SSR 路由 | 只为搜索/评论这类边缘需求引入服务端复杂度，收益不抵成本；筛选需求已用前端方案覆盖（见 ADR-0006）。 |
| 静态 + 边缘数据（KV/D1） | 当前无任何写入型需求，属于为假想的未来做设计。 |
